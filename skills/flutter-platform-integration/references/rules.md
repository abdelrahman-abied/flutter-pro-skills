# PLAT rules: what the checker reports, and why

`scripts/check_platform.py` is static and read-only. It needs only the Python
standard library and no `pub get`. Every hit is a candidate: read the code
before you call a finding `confirmed`. Each rule lists the false positives it
knows about and how to suppress a deliberate case.

The checker judges what the architecture, error and security checkers can't
see: where channels and native bindings live, whether platform errors and
`null` answers are handled, who owns native memory and stream subscriptions,
and whether plugins, isolates and permissions follow their contracts. Where a
concern already has an owner in the suite, PLAT cross-references it instead
of reporting it again (section 4).

## 1. How the checker reads the project

- **Scope.** Every `.dart` file under `lib/` that `arch_check` lists in
  `files[]`, minus barrels and `di` files. Generated files are skipped:
  `*.g.dart`, `*.freezed.dart`, files with a generated banner ("Autogenerated
  from Pigeon", "Autogenerated by jnigen", "AUTO GENERATED FILE … Generated
  by package:ffigen", "GENERATED CODE - DO NOT MODIFY"), and the output paths
  configured in `pigeons/*.dart` or `pigeon/*.dart` (`dartOut:`), a root
  `*.sh` running Pigeon (`--dart_out`), `ffigen.yaml` (or the `ffigen:` key in
  `pubspec.yaml`) and `jnigen.yaml`. Generated code is judged where your code
  calls it.
- **Pigeon APIs.** `@HostApi()` and `@FlutterApi()` class names are read from
  the Pigeon schema files, so constructing a host API (or calling
  `FlutterApi.setUp`) in a view counts as channel use (PLAT-001, PLAT-010).
- **Layers and roles** come from `../flutter-architecture/scripts/arch_check.py
  --json` (`files[]`). It reuses `$FPS_ARCH_JSON` when `dart-flutter-review`
  already ran it. Without the sibling skill, a path-based fallback is used and
  the `classification:` line says so.
- **Class kind decides placement.** A site inside a `State`/widget class is
  UI, inside a `ChangeNotifier`, `Cubit`/`Bloc`, `GetxController`,
  Riverpod notifier or `*ViewModel` it is logic, and inside any other class it
  belongs to a wrapper (never PLAT-001). Top-level code counts only in view
  and widget files, and never in the composition root.
- **"Layered".** An app has a data layer when arch_check reports a
  repository pattern or clean architecture, or any file sits in `data/` or
  has a source, service or repository role. PLAT-001 is Medium in layered
  apps and Low otherwise.
- **Project-wide facts.** Channel names are compared across files (PLAT-002);
  callers of a function that makes a platform call are found by name in every
  file (PLAT-003); platform interfaces are collected before implementations
  are checked (PLAT-009); permission handling is looked for anywhere in
  `lib/` (PLAT-012).
- **Placement notes.** Each finding's `note` carries the fix for the detected
  profile (`MVN: …`, `MVVM: …`, `Bloc: …`, `Riverpod: …`, `Provider: …`,
  `GetX: …`, plus `Clean: …` when the project has domain and data layers).
  Lifetime rules (PLAT-005/008) name the owner's own hook, from its supertype:
  `dispose()`, `close()`, `onClose()`, `ref.onDispose`. `--profile` overrides
  the detected pattern.
- **Suppression.** `// plat-ignore: PLAT-00x <reason>` on the reported line or
  the line above it; `// plat-ignore-file: PLAT-00x <reason>` anywhere in the
  file. The reason is kept in the JSON `suppressed` list.

## 2. Rules

### PLAT-001 channel-outside-data-layer

**Medium** in an app with a data layer · **Low** when the app has none (a
sample or a single-screen app) · all profiles

**Detects:** in a widget/State class or a logic class, any of:
`MethodChannel(`, `OptionalMethodChannel(`, `EventChannel(`,
`BasicMessageChannel(`, `.invokeMethod`/`invokeListMethod`/`invokeMapMethod`,
`.receiveBroadcastStream(`, `.setMethodCallHandler(`/`.setMessageHandler(`,
`DynamicLibrary.open/process/executable(`, `.lookupFunction<`,
`calloc`/`malloc`, `.toNativeUtf8()`, a Pigeon `@HostApi` constructor, or
`FlutterApi.setUp(`. Reported **once per file**, at the first site, with the
count. `SystemChannels.*` is never counted.

**Why:** a channel is I/O. In a widget or notifier it can't be faked in a
widget or unit test (every test needs a mock binary messenger), each caller
handles `PlatformException` its own way or not at all, and the channel
contract (method names, argument maps) leaks into presentation code. The
suite's architecture checker doesn't treat channels as I/O, so this rule owns
their placement.

```dart
// Bad: a notifier talks to the channel
@riverpod
class BatteryNotifier extends _$BatteryNotifier {
  static const _channel = MethodChannel('app.example/battery');
  @override
  Future<int> build() async => (await _channel.invokeMethod<int>('level'))!;
}

// Good: a source owns the channel, the repository maps errors, the notifier uses the repository
class BatteryPlatformSource {
  BatteryPlatformSource([this._channel = const MethodChannel(name)]);
  static const name = 'app.example/battery';
  final MethodChannel _channel;
  Future<int> level() async {
    final value = await _channel.invokeMethod<int>('level');
    if (value == null || value < 0 || value > 100) throw const FormatException('battery level');
    return value;
  }
}
```

**Profile notes:** the note names the home: MVN `data/sources/` behind the
repository contract; MVVM `data/services/`; Bloc a data-provider class given
through `RepositoryProvider`; Riverpod a source provider plus a repository
provider; Provider a root-built service; GetX a `GetxService`.

**Known false positives:** a widget-only file that is really a wrapper (move
it, or suppress with the reason); add-to-app modules that are one screen by
design (Low, since they rarely have a data layer).

**Not reported:** a channel in a plain wrapper class (wherever the file is),
in a source, service or repository, in the composition root (`main()`, DI),
or in a logic-shaped class under `core/`, `data/` or `domain/` (for example a
Riverpod keepAlive notifier that exposes platform paths: it *is* the data
provider).

### PLAT-002 channel-name-duplicated

**Low** · all profiles

**Detects:** the same channel name, as a plain string literal, passed to a
channel constructor at two or more sites in `lib/`. The first site (by path)
is the reference; every other site is reported, with the others listed.
Interpolated names (`'$prefix/method'`) and constants are fine.

**Why:** the name is the whole contract between Dart and the platform. Two
copies drift: one is renamed, the other silently throws
`MissingPluginException` on that path only. Tests that mock the channel by
name also miss the copy.

```dart
// Bad
final _channel = const MethodChannel('app.example/host');   // in two files

// Good
class HostChannel { static const name = 'app.example/host'; }
final _channel = const MethodChannel(HostChannel.name);
```

**Known false positives:** two independent packages in one repo using the
same public channel name on purpose (suppress one with the reason).

### PLAT-003 platform-call-unhandled

**Low** · all profiles

**Detects:** an `invokeMethod`/`invokeListMethod`/`invokeMapMethod` call that
can throw and that nothing catches:

- fired and forgotten (a bare statement or `unawaited(...)`) with no
  `.catchError`/`.onError`/`.ignore()`, so the error goes to the zone; or
- awaited or returned, with no `try` that catches `PlatformException`,
  `MissingPluginException`, `Exception`, `Object` or everything, and every
  caller found in the project (up to three hops, by name) also unguarded,
  ending in a framework callback (`onPressed:`, `listen(`, a State lifecycle
  method, an `_onX` handler) or a fire-and-forget call.

Results captured by `AsyncValue` (`@riverpod`, `FutureProvider`,
`AsyncNotifier.build`, `AsyncValue.guard`) or passed to
`FutureBuilder`/`StreamBuilder` count as handled. The rule is quiet when it
can't tell: no caller found, a closure passed somewhere else, an `@override`
method (called through an interface), or a common method name (`dispose`,
`start`, `load` …) that can't be matched across files.

**Why:** `PlatformException` is how native code reports failure, and
`MissingPluginException` is what you get on a platform, in a test or in an
isolate with no handler. Unhandled, both become uncaught async errors: the
spinner never stops and the user sees nothing. ERR-014 covers network calls
in UI callbacks; this is its channel-specific counterpart.

```dart
// Bad: the source throws, the repository passes it on, the button awaits it bare
onPressed: () async {
  final level = await repo.batteryLevel();
  setState(() => _level = level);
},

// Good: the repository maps it
Future<Result<int>> batteryLevel() async {
  try {
    return Result.ok(await _source.level());
  } on PlatformException catch (e) {
    return Result.error(BatteryFailure(e.code));
  } on MissingPluginException {
    return const Result.error(BatteryUnsupported());
  }
}
```

**Profile notes:** where to catch, per pattern (repository impl → `Failure`
for MVN and Clean, `Result.error` for MVVM, a failure state for Bloc,
`AsyncValue.error` for Riverpod). Load `flutter-error-handling` for the rest.

**Known false positives:** an error handler installed somewhere the checker
can't follow (a zone around a callback, a custom `Future` extension). Suppress
with the reason.

### PLAT-004 platform-result-force-unwrapped

**Low** · all profiles

**Detects:** `(await ch.invokeMethod<T>(...))!`; `await ch.invokeMethod(...)
as T` with a non-nullable `T` (type parameters are skipped); and a local
`final x = await ch.invokeMethod<T>(...)` later used as `x!` in the same
function with no null check (`== null`, `!= null`, `??`, `?.`, `is`, a
`switch`/`case`).

**Why:** `invokeMethod<T>` returns `Future<T?>`, and the native side can
answer `null` or a different type after an OS update, on another platform, or
when the implementation calls `result(null)`. `!` and a non-nullable `as`
throw a `TypeError`, which `on PlatformException` doesn't catch, so the error
path you wrote never runs.

```dart
// Bad
final result = await _channel.invokeMethod<int>('increment', {'count': value});
return result!;

// Good
final result = await _channel.invokeMethod<int>('increment', {'count': value});
if (result == null) throw PlatformException(code: 'no-result', message: 'increment returned null');
return result;
```

**Known false positives:** a protocol where `null` is impossible and covered
by a contract test (suppress the file with that reason).

### PLAT-005 event-subscription-dropped

**Medium** in a widget/State or logic class · **Low** elsewhere · all
profiles

**Detects:** `receiveBroadcastStream(...)` followed (possibly after
`.map`/`.where`) by `.listen(...)` as a bare statement: the
`StreamSubscription` is discarded, so it can't be cancelled.

**Why:** the native side starts producing events (sensors, location,
connectivity, battery) when the first listener subscribes and stops only when
the last one cancels. A dropped subscription keeps the native listener alive
for the life of the app, the callback runs after its owner is gone (`setState`
after dispose), and each new screen adds another.

```dart
// Bad: in initState
const EventChannel('app.example/charging').receiveBroadcastStream().listen(_onCharging);

// Good: the source exposes a Stream; the owner keeps and cancels the subscription
_sub = source.chargingChanges.listen(_onCharging);
@override
void dispose() { _sub?.cancel(); super.dispose(); }
```

**Profile notes:** the owner's hook: `dispose()` (State, ChangeNotifier, view
model), `close()` (Bloc), `onClose()` (GetX), `ref.onDispose` (Riverpod,
MVN).

**Overlap:** a subscription assigned to a name and never cancelled is the
`undisposed-resource` heuristic's (and UI-lifecycle's). PLAT-005 owns only
the discarded result and beats the heuristic on the same line.

**Known false positives:** an app-lifetime dispatcher in a background isolate
that listens forever by design (Low there; suppress with the reason).

### PLAT-006 native-memory-not-freed

**High** · all profiles

**Detects:** `calloc<T>(…)`, `malloc<T>(…)`, `calloc.allocate`/
`malloc.allocate`, and `toNativeUtf8()`/`toNativeUtf16()` without
`allocator: arena` (or another non-`calloc`/`malloc` allocator), inside a
function, when:

- the pointer is stored in a local (or a field) and the function (or class)
  never frees it (`calloc.free(p)`, `malloc.free(p)`, `free(p)`,
  `arena.free`), doesn't return it, doesn't attach it to a `NativeFinalizer`,
  doesn't pass it to an owning constructor or a `*Finalizable*` helper, and
  doesn't store it in a field or a list; or
- the allocation is passed **inline** as an argument (`fn(s.toNativeUtf8())`),
  so no reference is left to free.

Stored into a native array or struct field (`array[i] = s.toNativeUtf8()`) is
treated as owned by that container. Top-level `final` allocations are
app-lifetime and skipped.

**Why:** the Dart GC doesn't see native memory. A leaked `toNativeUtf8()` in a
method called per frame, per resume or per message grows the process until
the OS kills it, and leaked strings that held secrets stay readable in native
memory.

```dart
// Bad
int measure(String text) => _measure(text.toNativeUtf8());

// Good
int measure(String text) => using((arena) => _measure(text.toNativeUtf8(allocator: arena)));

// Good: long-lived native memory owned by a Dart object
final class NativeBuffer implements Finalizable {
  NativeBuffer(int length) : pointer = calloc<Int32>(length) {
    _finalizer.attach(this, pointer.cast(), detach: this);
  }
  static final _finalizer = NativeFinalizer(calloc.nativeFree);
  final Pointer<Int32> pointer;
}
```

**Known false positives:** a native function documented to take ownership
and free the memory itself (suppress with that reason, citing the API).

### PLAT-007 library-loaded-from-writable-path

**High** · all profiles

**Detects:** `DynamicLibrary.open(path)` where `path` is not a literal and
its expression, or the assignments to the locals it uses in the same
function, contain a path_provider directory (`getApplicationDocumentsDirectory`,
`getTemporaryDirectory`, `getApplicationSupportDirectory`,
`getApplicationCacheDirectory`, `getDownloadsDirectory`,
`getExternalStorageDirectory`, `getLibraryDirectory`),
`Directory.systemTemp`, `Platform.environment`, a text field's `.text`,
`Uri.base`, a file picker or `stdin`. A value only used in a condition (an
`if (Platform.environment.containsKey(...))`) doesn't count.

**Why:** loading a library runs its initialisers with the app's identity,
permissions and data. Every location above can be written by the app itself,
by a downloaded update, by another process on desktop, or by whoever controls
the environment, so this is a code-injection path (CWE-427/CWE-114).

```dart
// Bad
final dir = await getApplicationSupportDirectory();
return DynamicLibrary.open('${dir.path}/plugins/lib$name.so');

// Good: bundled with the app (native assets / build hooks, jniLibs, an embedded framework)
DynamicLibrary.open(Platform.isAndroid ? 'libtext.so' : 'text.framework/text');
```

**Known false positives:** a desktop app that verifies a signature or hash of
the file before opening it (suppress with the reason; prefer bundling).

### PLAT-008 call-handler-never-cleared

**Low** · all profiles

**Detects:** `.setMethodCallHandler(handler)` or `.setMessageHandler(handler)`
with a non-null handler inside a `State` or a logic class whose body never
calls the same setter with `null`. The note adds when it is registered in
`build()`, `didChangeDependencies()` or `didUpdateWidget()`, which re-register
on every call.

**Why:** the binary messenger keeps one handler per channel name. The handler
closes over the State or notifier, so after dispose a message from native
calls `setState` on a defunct State ("setState() called after dispose()") or
notifies listeners of a disposed ChangeNotifier. Two live owners also steal
each other's messages.

```dart
@override
void dispose() {
  _channel.setMethodCallHandler(null);
  super.dispose();
}
```

**Known false positives:** a root State that lives as long as the engine
(add-to-app modules); clearing it is still cheap.

### PLAT-009 platform-interface-not-enforced

**Medium** for `implements` · **Low** for a setter without `verify` · all
profiles

**Detects:** a class whose `implements` clause names a project class that
`extends PlatformInterface`, unless it also mixes in
`MockPlatformInterfaceMixin`; and a `PlatformInterface` subclass whose
`static set instance(...)` doesn't call `PlatformInterface.verify` or
`verifyToken`.

**Why:** federated plugins add methods to the platform interface in minor
versions, with a default that throws `UnimplementedError`. An implementation
that `extends` inherits the default; one that `implements` stops compiling
for every app on the next release. The token check makes sure only real
subclasses (and explicit test fakes) can be installed as `instance`.

```dart
class DesktopBattery extends BatteryPlatform { ... }     // not "implements"

static set instance(BatteryPlatform instance) {
  PlatformInterface.verify(instance, _token);
  _instance = instance;
}
```

### PLAT-010 isolate-channel-without-messenger

**High** · all profiles

**Detects:** `Isolate.spawn(entry, …)`, `Isolate.run(…)` or `compute(entry,
…)` whose entry point (a named function in the same file, or a unique one in
the project, or the closure passed) or a same-file helper it calls uses a
channel (`MethodChannel(`, `invokeMethod`, `receiveBroadcastStream`), a
Pigeon API, `SharedPreferences.getInstance`/`SharedPreferencesAsync`, or a
path_provider directory, with no
`BackgroundIsolateBinaryMessenger.ensureInitialized` in that code.

**Why:** platform channels need the root isolate's binary messenger. In a
spawned isolate the first call throws a `StateError` saying the background
messenger isn't initialized, and `RootIsolateToken.instance` is `null` there,
so the token has to be passed in.

```dart
final token = RootIsolateToken.instance!;
await Isolate.spawn(_entry, (token, ids));

Future<void> _entry((RootIsolateToken, List<String>) args) async {
  BackgroundIsolateBinaryMessenger.ensureInitialized(args.$1);
  ...
}
```

**Known false positives:** the call happens in a helper in another file that
initialises the messenger itself (suppress with the reason).

### PLAT-011 permission-requested-at-startup

**Low** · all profiles

**Detects:** `Permission.<x>.request()` or `[Permission.a, …].request()`
(permission_handler) inside `main()`, `bootstrap()`, `mainCommon()`, or at top
level of `lib/main*.dart`.

**Why:** a system prompt with no context is the likeliest to be denied, and
on iOS (and on Android after two denials) a denial is permanent: the app can
only send the user to Settings from then on. Asking when the user taps "Scan"
gets the context for free. This automates `SEC-permission-overreach` for the
startup case.

### PLAT-012 permanent-denial-unhandled

**Low** · all profiles

**Detects:** permission requests (as in PLAT-011, anywhere) in a project where
nothing in `lib/` mentions `isPermanentlyDenied`, `permanentlyDenied`,
`isRestricted`, `openAppSettings(` or `AppSettings.open…(`. Each request site
is reported.

**Why:** after a permanent denial `request()` returns `permanentlyDenied`
immediately, with no prompt. Without handling it the feature silently does
nothing; the fix is a settings link.

```dart
final status = await Permission.camera.request();
return switch (status) {
  PermissionStatus.granted || PermissionStatus.limited => CameraAccess.granted,
  PermissionStatus.permanentlyDenied || PermissionStatus.restricted => CameraAccess.blocked,  // view offers openAppSettings()
  _ => CameraAccess.denied,
};
```

## 3. Reading-level findings (PLAT-<slug>)

The checker can't see these reliably. Look for them when you review platform
code.

| ID | Severity | Look for | Fix |
|---|---|---|---|
| PLAT-unvalidated-native-value | Medium | values from native (`invokeMethod` results, event payloads, Pigeon fields) used without range, enum or shape checks; `event[0] as double` on an untyped list | validate at the source boundary and throw a typed exception; prefer Pigeon's typed classes |
| PLAT-sensitive-data-over-channel | Medium | tokens, passwords, full profiles or PII sent to native code that doesn't need them, or channel payloads logged | send the minimum; keep secrets in `flutter_secure_storage` (`flutter-secure-defaults`) |
| PLAT-sync-ffi-on-ui-isolate | Medium | a long synchronous FFI call (parsing, crypto, image work, disk) in `build()`, a gesture callback or a frame callback | `Isolate.run`, a long-lived worker isolate, or an async native API (`ffi.md` §4) |
| PLAT-platform-view-in-list | Medium | `AndroidView`, `UiKitView`, `AppKitView`, `HtmlElementView` built per item in a scrolling list, or animated/transformed every frame | one platform view outside the list, a static snapshot, or a Flutter-native widget (`plugins-and-platform-views.md` §3, `flutter-performance`) |
| PLAT-handwritten-channel-api | Low | a hand-written channel API that has grown past a couple of methods, with string method names and `Map` arguments | Pigeon (`channels-and-pigeon.md` §3) |
| PLAT-platform-check-in-widget | Low | `Platform.isX`/`kIsWeb`/`defaultTargetPlatform` checks in widgets deciding whether a native call will work | an "unsupported" result from the source; widgets render it Now automated as `ADAPT-001` (dart:io `Platform` in a web app) and `ADAPT-002` in `flutter-adaptive-layout` (`../flutter-adaptive-layout/SKILL.md`); report the ADAPT id. |
| PLAT-generated-code-edited | Low | hand edits in Pigeon/ffigen/jnigen output, or generated files reviewed line by line | change the schema or config and regenerate; review the schema |
| PLAT-no-channel-fake | Low | logic tests that need the engine because the channel or source can't be injected | constructor-inject the channel or source (`testing-platform-code.md`) |

## 4. Not checked here (cross-references)

| Concern | Owner | Why PLAT stays out |
|---|---|---|
| HTTP and database I/O in widgets and logic | ARCH-005 / ARCH-007 / ARCH-101 | arch_check doesn't treat channels as I/O; PLAT-001 owns channel placement |
| generic swallowed, untyped or `Error` catches | ERR-001 / ERR-002 / ERR-003 | PLAT-003 is only about the missing platform-exception path |
| unguarded network I/O in UI callbacks | ERR-014 | |
| which permissions to ask for; secrets and tokens in storage, logs or channels | SEC-* and SEC-permission-overreach (`flutter-secure-defaults`) | PLAT-011 automates the startup case and beats SEC-permission-overreach there |
| iOS usage descriptions, Android manifest permissions for release | REL-009 (`flutter-release`) | |
| heavy Dart work on the UI isolate | PERF-011 (`flutter-performance`) | PLAT owns only synchronous FFI calls (reading level) |
| platform-view cost, profiling jank | `flutter-performance` | |
| undisposed controllers; subscriptions assigned and never cancelled | UI-lifecycle, `undisposed-resource` heuristic | PLAT-005 owns the discarded `receiveBroadcastStream().listen` |
| test strategy, fakes vs mocks | `flutter-testing` | |

**The canonical apps have no high or medium hits.** Their lows are true
positives on reading: channels and handlers inside States and
ChangeNotifiers in apps without a data layer (Low by design), `result!` on
`invokeMethod<int>` in the platform_channels counter (a `null` answer becomes
a `TypeError` that the demo's `catch (error) { error as PlatformException }`
turns into a second crash), a handler registered in `didChangeDependencies()`
and never cleared, and fire-and-forget `invokeMethod<void>` calls in the
add-to-app models whose `MissingPluginException` would be an uncaught async
error.

**Other true positives.** hiddify passes five `toNativeUtf8()` strings
(including a generated secret) straight into the core library's setup call,
which runs again on every resume, so they leak each time; and it writes its
